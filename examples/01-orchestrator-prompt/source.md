# Example 01: Agentic Orchestrator Prompt (full FM-XX coverage)

> Real prompt template generated by `vibecoding-engineer` for an agentic orchestrator that invokes N skills to produce automated deliverables. Shows the canonical format with all sections including `## Anti-pattern blocked` and `## Test gate suggested`.

## Context

Stack: Vite + React + TypeScript + Postgres + serverless edge functions.
Architecture: an agentic AI orchestrator that invokes N skills to generate autopilot deliverables. Single-resource user, multi-resource registry.
Infra constraints: row-level security on the database, no admin credentials in the client, env vars in a secret manager.

## Requirement

REQ-ORC-002: the orchestrator must invoke skills in a goal-aligned sequence. Every skill emits artifacts that the next step consumes. The orchestrator must NOT run in circles, invoking skills with no purpose.

## Constraints

- OWASP Agentic ASI01 (Agent Goal Hijack): the orchestrator cannot accept goal redefinition at runtime
- OWASP Agentic ASI06 (Memory & Context Poisoning): artifact schema validation before persisting
- Rate limit: max 30 skill invocations per user-resource per 24h
- Budget: max 50k tokens per orchestrator run, soft cap (not a hard cut)

## Anti-pattern blocked

- **FM-01**: the orchestrator does not run in circles. Every skill invoked MUST log `goal_alignment_score` (numeric, 0-1); a periodic audit aborts the run if avg(score) < 0.6 over the last 5 steps.
- **FM-02**: stop conditions are not a hard budget cut. Stop = quality_gate reached OR user_paused=true OR error_rate > 0.3.
- **FM-04**: skills are discovered at runtime through a capability registry, with no hardcoded skill list. Adding a new skill does not break the existing orchestrator.
- **FM-05**: atomic lock on (user_id, resource_id) before an orchestrator run starts. Parallel runs on the same (user, resource) are interrupted cleanly.

## Expected output

- `src/orchestrator/goal-aligned-orchestrator.ts` (core logic)
- `src/orchestrator/types.ts` (artifact schema + goal_alignment_score field)
- `src/orchestrator/capability-registry.ts` (runtime skill discovery)
- `db/migrations/<YYYYMMDD>_orchestrator_run_lock.sql` (lock table)
- `tests/orchestrator/orchestrator-goal-filter.test.ts` (test gate FM-01)
- `tests/orchestrator/stop-conditions.test.ts` (test gate FM-02)
- `tests/orchestrator/capability-registry-discovery.test.ts` (test gate FM-04)
- `tests/orchestrator/concurrent-run-lock.test.ts` (test gate FM-05)

## Acceptance criteria

- [ ] Every skill invocation logs `goal_alignment_score` (numeric, 0-1) in the `orchestrator_run_steps` table
- [ ] The audit job reads the log and aborts the run if `AVG(goal_alignment_score) < 0.6` over the last 5 steps
- [ ] Stop condition: NOT a hard cut on the token cap. Stop = `(quality_gate=true) OR (user_paused=true) OR (error_rate > 0.3)`
- [ ] A new skill is added through `capability_registry.register(skillId, metadata)`, with no orchestrator rebuild
- [ ] Atomic lock via `SELECT FOR UPDATE` on the `orchestrator_runs(user_id, resource_id)` row; the second concurrent run receives `ConcurrentRunError` and stops cleanly
- [ ] Test gates FM-01, FM-02, FM-04, FM-05 green in CI

## Test gate suggested

```bash
npm test -- orchestrator-goal-filter.test.ts
npm test -- stop-conditions.test.ts
npm test -- capability-registry-discovery.test.ts
npm test -- concurrent-run-lock.test.ts
```

All of them must pass. If one fails, the PR is blocked.
